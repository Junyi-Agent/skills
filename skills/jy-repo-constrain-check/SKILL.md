# Repo 流程约束检查

只检查、只报告，几分钟内完成。不修改任何文件，不跑测试、不触发 hook，不启动 subagent。

## 第 1 步：跑脚本

```bash
python3 <本 skill 目录>/scripts/check.py get checks --repo <repo 路径>
```

不给 `--repo` 时用当前目录。脚本只读，默认一次扫完八项（只看某几项时在 `checks` 后写编号，如 `get checks 7 8`），每项给出初判和带 `文件:行号` 的证据片段：

- PASS / WARN / FAIL：脚本根据事实已能判定
- JUDGE：找到了相关内容，但是否合格要读懂语义，由你判断
- N/A：不适用（目前只有第 8 项会出现，表示脚本初判为 app 类 repo）

输出第一行是识别到的语言（`-o json` 里是 `languages` 字段）。容易跨语言误判的规则只对这些语言生效，没识别到任何语言时全部生效，见 `rules/README.md`。

默认会用 `gh api` 查一次 GitHub 分支保护（6 秒超时）；离线或不想访问网络时加 `--no-remote`。加 `-o json` 时输出同样内容的 JSON（供其他程序处理）；参数错误、路径不存在或不是目录时退出码为 2。

## 第 2 步：判定 JUDGE 项

只看脚本给出的证据片段，片段不够时再读对应文件的那几行，不要通读 repo。各项的合格标准：

1. **ADR**：状态字段有这三种，且 repo 里写明了各自含义：
   - **提议**（Proposed）：只写了 ADR 文档
   - **采纳**（Accepted）：允许去实现，可能已经实现
   - **已验证**（Verified）：人类测试了代码，确认了实现的内容

   只有提议/采纳、没有“已验证”这一档时算 WARN（标准 ADR 的 Accepted 只表示同意实现，不代表实测过）。有“已验证”但没写明它要求人类实测时，也算 WARN
2. **pre-commit 安装**：本机已安装，且 repo 里写了安装步骤（新机器、重建的 worktree 能装上）
3. **formatter + 严格 linter**：两类都在 pre-commit 里，linter 开了严格模式，且没有 `--exit-zero`、`|| true` 之类的放宽
4. **agent 审查门禁**：由已安装的 hook 触发、覆盖 worktree squash merge 后的 push；3 个 agent 的审查方向不同；≥2 同意才放行，否则非零退出阻止 push。缺任一条就不是 PASS，写明缺哪条
5. **worktree 规则**：README / CLAUDE.md / AGENTS.md 至少一处明确规定：每个新功能在当前目录之外建 worktree，且不在当前目录切换分支。只说“可以用 worktree”算 WARN；worktree 出现在产品功能介绍里（比如工具本身管理 worktree）不算流程规定
6. **脚本强制**：有会阻断的约束（PreToolUse 返回 block/deny、git hook 非零退出），覆盖第 4、5 项的流程。只有辅助脚本、靠 agent 自觉调用的，算 WARN
7. **CI/CD**：PR 和主分支 push 都触发；跑 lint 和测试，且与 pre-commit 一致；没有放宽；主分支要求检查通过才能合并。需要发布的项目还应有 CD
8. **Unix 设计哲学（只查工具类 repo）**：先定类型，再判定。
   - **工具类**：主要给人在终端里用或给其他程序调用，比如 CLI、库、脚本集合、hook。**app 类**：面向终端用户的 web、移动、桌面应用或长期运行的服务。脚本给出类型初判和依据，以你读到的为准；两类都有时（比如 app 带一个运维 CLI）只查工具部分
   - app 类：结论写“不适用”，依据写明判定为 app 的理由，不计入 ⚠️ / ❌，也不列补法
   - 工具类按以下几条判定，全部满足 ✅，缺一两条 ⚠️，大多不满足 ❌：
     - **kubectl 式命令结构（必须项）**：每个给人或其他程序按名字调用的命令行入口都满足下面三点。只有一个功能的工具也算在内。入口的参数由调用方定死的不算，比如 git hook、Claude Code hook
       - 格式是 `<tool> <动词> <资源> [名字] [flags]`，比如 `kubectl get pods`、`kubectl delete deployment web`
       - 不同资源用同一套动词（get / list / describe / create / delete / apply 等），不为每种资源另起动词
       - 输出格式统一用 `-o` / `--output` 选（如 `-o json`、`-o yaml`）
     - **豁免**：只有人类同意才能豁免，且必须写 ADR。ADR 状态为采纳或已验证，写明豁免哪个入口、豁免理由、哪位人类批准。脚本列出提到豁免的 ADR，你逐篇核对这几项；状态是提议、缺任一项，或豁免对象不是这个入口，都不算豁免。依据里写明用了哪篇 ADR
     - 不满足 kubectl 式结构又没有有效豁免时，第 8 项最多 ⚠️，不能给 ✅；补法写成“改成 `<tool> <动词> <资源>` 结构，或请人类批准后写豁免 ADR”
     - 一个命令只做一件事；功能多时拆成子命令或独立命令，不把无关功能塞进同一个入口
     - 文本流接口：能从 stdin 或文件读输入，结果写 stdout，日志、进度和错误写 stderr，能放进管道
     - 输出可被程序处理：默认是纯文本行，并能用 `-o json` 之类的选项切到机器可读格式；输出不是终端时不带颜色和进度条
     - 退出码有意义：成功 0，失败非零，调用方能据此判断
     - 安静：成功时不打印多余信息
     - 不强制交互：所有输入都能通过参数、环境变量或 stdin 给出，不在非终端环境里卡在提问上

脚本初判为 PASS/WARN/FAIL 的，一般直接采用；证据明显与初判矛盾时以证据为准，并说明原因。

## 第 3 步：输出

在对话里输出，不写文件（用户要求时才写）：

```
| # | 检查项 | 结论 | 依据 |
|---|---|---|---|
| 1 | ADR 提议/采纳/已验证 | ⚠️ | docs/adr/ 有 6 篇，状态只有 Proposed / Accepted，没有“已验证”这一档 |
...
| 8 | Unix 设计哲学 | 不适用 | app 类：Next.js 前端 + API 服务，没有 CLI 入口 |
```

结论用 ✅ / ⚠️ / ❌，第 8 项对 app 类 repo 写“不适用”。表后列出所有 ⚠️ 和 ❌ 的补法，每条一句，具体到文件和要加的内容，按“补上后对防止 agent 偏移最有用”的顺序排。全部 ✅ 时只输出表格。
