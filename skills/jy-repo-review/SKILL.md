# Repo 审查

对 repo 做一次只读审查，产出 REVIEW.md。全程不修改 repo 里的任何代码文件；工具输出、复现脚本等临时产物一律放在 repo 之外的临时目录。修复是另一轮的事，由用户看完报告后决定。

流程：确定范围 → 跑工具并建地图 → 分组并行审查 → 独立核实 → 汇总。核实一步不能省，也不能由提出发现的 agent 自己做：审查者倾向于维护自己的结论，而且很多“问题”其实是故意的设计，只有带着“试图推翻它”的任务去查，才能查出来。

## 第 0 步：确定范围和已知约定

1. 确定审查范围。用户没指定时，默认审源码和测试，忽略 vendored 依赖、生成代码、lock 文件、数据文件。
2. 读 CLAUDE.md、README、docs/ 下的设计文档或 ADR，找出项目约定。
3. 查找“已知的故意设计”清单（通常在 CLAUDE.md 的同名小节，或 REVIEW_NOTES.md）。清单里的条目不再作为问题上报。
4. 用 tokei、cloc 或 wc 估一下有效源码行数，决定规模策略：
   - 约 3000 行以下：不开审查 subagent，自己按四组维度依次审；核实步骤仍然用全新的 subagent。
   - 约 3000 到 1 万行：按下面的四组并行。
   - 更大：按“模块 × 组”切分，或先和用户确认只审核心模块。审不完时用 git 历史定优先级：改动最频繁的文件、最近大改过的模块先审（例如 `git log --since="6 months ago" --name-only --format=` 统计各文件出现次数）。
5. 决定全量还是增量：
   - 用户要求全量，或 REVIEW.md 里没有记录基线 commit：做全量审查。
   - 否则做增量审查：只审基线 commit 以来改动的文件（`git diff --name-only <基线>..<第 6 条固定的 commit>`），以及调用这些改动的代码。另外逐条检查上次报告里“确认的问题”是否还在，还在的保留到新报告。已修复的不能直接去掉，要同时审修复本身：修得完整吗（同一问题的其他位置是否一并修了）、有没有引入新问题。修复完整的去掉；不完整的保留，写明哪部分没修好；修复引入的新问题作为新发现上报。在报告开头注明这是增量审查及其范围。
6. 固定审查对象。记下当前 commit（`git rev-parse HEAD`），用 `git worktree add <临时目录>/review-<hash> <hash>` 建一份拷贝，当作只读使用。之后第 1 步的工具和测试、所有 subagent 的读代码、跑工具、跑测试，都在这份拷贝里进行，每个 subagent 的 prompt 里写明这个路径和 commit。不在用户的工作目录里读代码，因为那里可能有别的会话在改，未提交的改动也不属于审查对象。审查结束后用 `git worktree remove` 删掉这份拷贝。

## 第 1 步：跑确定性工具，建立模块地图（自己做）

通读目录结构和入口文件，写一份简短的模块地图：每个模块的职责、模块间依赖方向、主要入口、公开 API。后面每个 subagent 都会拿到它，避免各自重新摸索。

同时跑一遍确定性工具，把输出存到临时目录。工具便宜且不漏，让 subagent 把精力留给工具查不出的问题：

- 优先用项目已经配置的工具（看 pyproject.toml、package.json、Makefile、CI 配置）：linter、类型检查、测试套件。
- 环境里现成或一条命令能装的再补：死代码检测（如 Python 的 vulture、ruff 的未使用项规则）、依赖审计。
- 只跑检查，不用任何自动修复选项（不加 `--fix` 之类）。
- 按 README 的步骤实际跑一遍构建和测试，记录哪一步失败或与文档不符。这是可复现性的直接证据。
- 某个工具跑不起来就跳过，在报告里写明哪些没跑、为什么。

## 第 2 步：四组并行审查

在同一轮里启动 4 个 subagent。每个的 prompt 包含：模块地图、审查范围、项目约定和已知故意设计清单、它负责的维度、与该组相关的工具输出、下面的输出格式。

1. **正确性**：逻辑 bug 与边界情况、错误处理（被吞的异常、静默失败）、并发与资源泄漏、测试质量（断言是否真的在验证行为、主路径是否有测试）。另外专门找缺失的东西：没做的输入校验、没处理的失败路径、没覆盖的边界情况。审查天然偏向挑已有代码的毛病，缺了什么要主动去想
2. **清理**：死代码、冗余或重复代码、未使用或过时的依赖
3. **一致性**：文档漂移（README、docstring、注释、CLI help 与代码不符）、配置漂移（默认值多处定义且矛盾）、命名与惯用法不统一、过期的 TODO
4. **设计与工程**：架构清晰度、模块边界与依赖方向、抽象是否恰当、接口易误用之处、安全问题、热路径上的明显性能浪费、可复现性。报用户确认流程（操作前是否征得用户同意、哪些操作免确认）或权限范围（工具权限分级、系统权限申请）相关的问题前，先查 ADR 是否已经明文接受这种取舍；已接受的不报，实现与 ADR 写的不一致时照常报。另外检查命令行入口的结构，见下一段

**命令结构（设计与工程组负责）**：每个给人或其他程序按名字调用的命令行入口，都要是 kubectl 式结构；只有一个功能的工具也算在内。入口参数由调用方定死的不查，比如 git hook、Claude Code hook。要求三点：

- 格式是 `<tool> <动词> <资源> [名字] [flags]`，比如 `kubectl get pods`、`kubectl delete deployment web`
- 不同资源用同一套动词（get / list / describe / create / delete / apply 等），不为每种资源另起动词
- 输出格式统一用 `-o` / `--output` 选（如 `-o json`、`-o yaml`）

不满足的入口逐个上报，严重度为中，证据里写出现在的调用形式和不满足哪一点。只有一种情况不报：有一篇 ADR 豁免了这个入口，状态为采纳或已验证，并写明豁免对象、理由和批准的人类。ADR 状态是提议、缺理由或批准人、豁免的是别的入口，都照常上报，并在证据里写明这篇 ADR 缺什么。

每条发现的格式：

```
- 位置：文件:行号
- 问题：一句话
- 证据：具体的失败场景，或是如何确认的（例如搜索了哪些调用点）
- 严重度：高 / 中 / 低
```

对审查 subagent 的要求：宁缺毋滥；不报风格偏好和泛泛的建议；没有具体位置和证据的不报。工具已经报出的条目不用逐条重复，同类的合并成一条并注明数量；工具报出但判断为误报的，说明理由。

一条发现涉及多个位置时（「N 处重复」「另一处同样过期」「与其他 X 都不一致」），每个位置都要单独读代码确认，并在证据里逐一写出。没有逐一确认的位置不要列进去。只是写法相似、但条件或行为不同的，不算重复。

**代码分块（一致性组负责）**：函数体、方法体或脚本里，做不同事的几段代码之间要空一行，比如解析参数、校验、计算、输出各成一段。这样人类可以一块一块读，不用一行一行读。这是项目要求，不算“风格偏好”，要上报：

- 报：一段连续没有空行的代码里有两件以上不同的事。只用注释隔开、没有空行的，也算没分块
- 不报：只做一件事的短函数；一个长的字面量或配置表；formatter 已经管的空行（顶层定义之间）
- 证据写出行号范围，以及这段代码混在一起的是哪几件事。同一文件的多处合并成一条，每处单独确认并列出行号范围。严重度为低

## 第 3 步：由全新的 agent 独立核实

先自己合并四组结果并去重，然后启动新的 subagent 做核实。这些核实者必须是新启动的，不能复用第 2 步的 subagent。

**给核实者什么**：只给每条发现的位置和问题陈述，加上模块地图和项目约定。不要给审查者的证据和推理，让核实者自己从代码出发得出结论，否则它只会顺着原来的思路走。

**核实者的任务**：试图推翻每条发现。对每一条依次回答：

1. 这个现象真的存在吗？亲自读代码确认，不要相信陈述。
2. 它是故意的吗？查这些地方：
   - 附近的注释和 docstring
   - `git log` 和 `git blame` 里相关提交的说明
   - 设计文档、ADR、CLAUDE.md、README
   - 是否有测试专门断言了这个行为
   - 代码里是否有同样的模式被反复、一致地使用（一致的重复更像约定，不像疏忽）
3. 死代码类额外检查：动态调用、反射、字符串引用、对外导出的入口、被脚本或配置引用。命令结构类只认第 2 步说的豁免 ADR：注释、提交说明、整个 repo 一致的写法都不能让它归为“故意设计”，也不归“无法判断”。
4. 如果是真问题，严重度定得合理吗？
5. 正确性类的发现要尝试复现：在 repo 之外的临时目录写一个最小复现脚本或失败的测试并实际运行。跑出失败的，把复现方式和输出写进依据；合理努力后仍无法复现的，标明“未复现”并说明原因（例如需要特定硬件、难以构造的并发时序），不要因此直接判为证伪。

涉及多个位置的发现，逐个位置给结论，写明哪几处成立、哪几处证伪。

**核实结论**，四选一，并附依据：

- **确认**：现象存在，且找不到故意为之的证据
- **故意设计**：找到了明确依据（写明是哪条注释、哪个提交、哪份文档）
- **证伪**：现象不存在，或审查者理解错了
- **无法判断**：现象存在，像是故意的但没有文字依据，或需要只有作者知道的背景

没有文字依据时不要猜成“故意设计”，归到“无法判断”，交给用户回答。

代码分块类的发现，整个 repo 都不空行、formatter 没加空行，都不能当作故意设计的依据。核实者只看这段代码是不是真的混了几件不同的事。

**分批**：按文件或模块把发现分给核实者，每个核实者大约 10 条，并行启动。高和中严重度的全部核实；低严重度的条目多时可以抽查，并在报告里说明没有逐条核实。

## 第 4 步：汇总成 REVIEW.md

结构：

1. **总体评价**：两三句话，加上建议的修复顺序（通常是：删死代码 → 修 bug → 重构 → 更新文档）
2. **确认的问题**：按严重度排序，每条带位置、问题、核实依据
3. **需要你确认**：所有“无法判断”的条目，每条写成一个可以直接回答的问题，例如“`foo.py:42` 失败后返回空列表而不抛异常，是有意的吗？”
4. **判定为故意设计**：每条带依据。对其中没有注释说明的，建议补一句注释，或记入已知故意设计清单
5. **统计**：各组上报多少条、确认多少、故意设计多少、证伪多少。证伪的条目不用列出。如果旧的 REVIEW.md 里有上次的统计，把两次并列；某一组的证伪率连续偏高时，在这里指出，建议收紧这个 skill 里对该组的要求
6. **基线**：第 0 步固定的 commit hash 和日期（不是汇总时的 HEAD），以及没跑成的工具。审查期间 HEAD 有新提交的，列出这些提交，注明不在本次范围内。下次增量审查以这个 commit 为起点

最后在对话里简要告诉用户结果，并问一句：是否把“故意设计”和用户确认过的条目写入已知故意设计清单，这样下次审查不会重复上报。用户同意后才写。
