# 0004 命令行入口用 kubectl 式结构，豁免要人类批准并写 ADR

状态：采纳

## 背景

`jy-repo-constrain-check` 第 8 项只要求“功能多时拆成子命令或独立命令”，没有规定子命令怎么组织；`jy-repo-review` 不检查命令结构。不同工具各起各的命令格式，人和 agent 都要逐个记用法。

## 决策

- 每个给人或其他程序按名字调用的命令行入口，都用 kubectl 式结构：`<tool> <动词> <资源> [名字] [flags]`，不同资源复用同一套动词，输出格式用 `-o` / `--output` 选。只有一个功能的工具也适用。入口参数由调用方定死的（git hook、Claude Code hook）不适用。
- 这是必须项。`jy-repo-constrain-check` 里不满足又没有有效豁免时，第 8 项最多 ⚠️；`jy-repo-review` 把不满足的入口作为中严重度问题上报，核实时只认豁免 ADR，不因注释或一致写法归为故意设计。
- 豁免只在人类同意时成立，且必须写 ADR：状态为采纳或已验证，写明豁免哪个入口、理由、批准的人类。
- `check.py` 列出代码里声明的子命令名和提到豁免的 ADR，具体是否合格由 agent 读代码判断。

## 后果

- 检查方式是正则找线索加 agent 判断，识别不了的参数解析写法（手写 `sys.argv` 分发等）要靠 agent 读入口代码。
- 本仓库自己的 `check.py`、`ablation_report.py` 目前不是这种结构，需要改造或由人类批准豁免。
