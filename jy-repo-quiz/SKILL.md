# Repo Quiz

目标：检验用户是否真正理解这个 repo，而不是能否背出名字。全程只读，不修改任何文件。

## 参数（均可选，从用户的话里解析）

- 范围：子目录、模块或主题（默认整个 repo）；也可以是一段变更，如「最近 20 个 commit」「某个 PR / 分支」「某个 commit 之后」
- 题数：默认 8
- 难度：入门 / 标准 / 刁钻（默认标准）

缺省时直接用默认值开始，不要先问一轮。

## 第 1 步：读 repo，建立设计地图

读的过程中不要向用户复述发现，否则等于泄题。只说一句「正在读 repo」。

按顺序读：

1. README、docs/、CLAUDE.md / AGENTS.md、设计文档、ADR
2. 目录结构、构建与依赖配置、入口点
3. 核心模块：沿一条主路径（一次请求 / 一次任务 / 一次推理）从入口追到底
4. `git log` 里的大改动和 commit message，找设计取舍的来由
5. 测试：它们暴露了哪些不变量和边界情况

repo 很大时，用 Explore 子代理按模块并行读，每个返回：职责、对外接口、关键不变量、不显然的设计决定（带 `文件:行号`）。

范围是一段变更时：先用 `git log` / `git diff` 读这段变更本身，再读它触及的模块和调用方，够理解上下文即可，不必通读整个 repo。题目围绕这段变更：改了什么、为什么改、引入了哪些新的不变量或耦合、对未改动的代码有什么影响。

在内部整理出一张设计地图：

- 模块及其边界，谁依赖谁
- 主数据流 / 控制流
- 关键设计决定，以及被放弃的替代方案；每条标注理由的出处（commit message、注释、文档），没有出处的标为「推测」
- 不变量、并发与生命周期假设、错误处理策略
- 容易被误解的地方（看起来像 bug 的故意设计、隐含耦合、性能关键路径）

## 第 2 步：开场自述

读完后、出题前，先请用户用几句话讲一遍范围内的整体设计：有哪些主要模块，主路径怎么走，最关键的设计决定是什么。范围是一段变更时，改为讲这段变更做了什么、为什么。

把自述和设计地图对比，在内部记下讲错的和完全没提到的部分，此时不点评、不纠正，只说一句「好，开始出题」。后面的题优先打在这些地方；用户讲得准确的部分少出或不出。

用户说跳过自述，就直接出题。

## 第 3 步：出题

每道题必须有代码依据：出题前回到源码核实答案，记下 `文件:行号`。核实不了的题就丢掉。

题型配比（标准难度）：

- 架构，约 40%：模块职责、边界、数据流。例：「请求从 X 进来到 Y 落盘，中间经过哪几层，各自负责什么？」
- 设计理由，约 25%：为什么这样做，而不是另一种做法。只有理由有出处（commit message、注释、文档）时才作为计分题，反馈时引用出处。理由只是推测时，不要编一个标准答案去判对错：改成不计分的讨论题，明说「这里没有找到作者的说明」，听用户的看法后给出自己的推测及其依据。有出处的理由题不够时，把配额让给反事实题
- 细节，约 20%：不变量、边界情况、某个函数在特定输入下的行为
- 反事实，约 15%：「如果把 A 改成 B，哪里会坏？」「这个 bug 现象最可能出在哪一层？」

出题要求：

- 考理解，不考记忆。不出「这个函数叫什么」「在哪个文件」这类题
- 每题只考一个点，题干自带必要上下文
- 选择题的干扰项要是真实存在的误解，不要一眼假
- 由浅入深：先整体架构，再下探细节
- 入门难度多用选择题；刁钻难度以开放题和反事实题为主

## 第 4 步：交互式作答

一次只出一题，等用户答完再出下一题。每题请用户顺带报信心：确定 / 不确定。用户没报就不追问，按未报处理。

- 选择题用 AskUserQuestion（没有该工具就用纯文本列选项）
- 开放题让用户直接打字回答

每题答完立刻反馈：

1. 判定：对 / 部分对 / 不对。如实判，不放水
2. 正确答案和原因，引用 `文件:行号`
3. 用户答错时，指出其心智模型具体偏在哪里

自适应：某个方向答错，后面追加一道同方向的变式题；连续答对，提高难度。用户说「跳过」「不知道」就直接讲解并继续。用户对判定有异议时，回到源码重新核实，错了就承认并改分。

## 第 5 步：总结

全部答完后给出：

- 得分，以及按题型（架构 / 理由 / 细节 / 反事实）的分项情况
- 薄弱点：具体到哪个模块或哪个概念
- 确定但答错的题：单独列出，这些是最需要纠正的误解；不确定但答对的题也提一句，说明这块理解还不稳
- 开场自述里讲错或漏掉、而 quiz 没覆盖到的点
- 补读清单：3 到 5 个最值得读的文件或函数，各附一句为什么

只在用户要求时把题目和解析写成 QUIZ.md。
